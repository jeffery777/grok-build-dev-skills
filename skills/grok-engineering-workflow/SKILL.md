# Bounded engineering work in Grok Build

Read the complete fixed [workflow](../../vendor/engineering-workflow-core/contracts/workflow.md) and [authorization and stops](../../vendor/engineering-workflow-core/contracts/authorization-and-stops.md). Read [Grok capability mapping](../../references/grok-capabilities.md) before selecting tools or delegating. These Chinese-authoritative Core bytes define obligations; this skill supplies the Grok mapping and grants no tools or external-write authority.

Establish the current request, repository/branch/HEAD/upstream, complete diff, scope, DoD and single-writer ownership. Preserve unrelated changes. Reuse still-valid evidence and select the smallest coherent implementation. Follow applicable project rules for Issue/branch creation and external actions.

Check the actual loaded public tool schemas and effective model/effort, sandbox and permissions for the selected surface. Keep documented, schema-observed and runtime-verified evidence separate. The offline package/packet commands prove local structure only. Current Grok runtime qualification is incomplete: stop dependent model/tool execution unless the required controlled qualification and authorization already exist. Continue safe independent preparation without lowering DoD.

Use native Grok subagents when they are available, authorized and qualified for the task. Do not substitute Codex dispatch names or build a replacement pool. Assign bounded inputs, source revision, ownership, output and stop conditions. A dispatched ID alone is not completion; collect the actual result and verify it. Missing/disabled/unknown delegation means a single writer plus a separately authorized independent reviewer, not author self-approval. Do not create peer sessions or paid API calls merely because a task can be described in a skill.

Implement and verify the bounded change. Read [review and security](../../vendor/engineering-workflow-core/contracts/review-and-security.md) and obtain an independent read-only [change review](../grok-review-change/SKILL.md); complete applicable security scans and resolve all findings. A plan/persona label is not technical read-only enforcement. If such enforcement is required, demand actual tool/deny evidence.

Synchronize behavior, docs, package and version claims. For a change request or delivery readiness, read the complete [exact-head contract](../../vendor/engineering-workflow-core/contracts/exact-head-and-evidence.md): verify and independently review the entire base-to-head range for every changed head. Separate content readiness, platform enforcement and action authority. External commit/push/PR/merge requires action-specific authority and all applicable gates. Use the delivery entry point explicitly authorized by the current project and request; this skill grants no external-write authority.

Preserve unresolved questions, checkpoints and uncertain effects. Forward new authorization requests with the full question, original request, session/revision/action/path identity and limits; stop and wait. Never infer consent from timeout, a new session or a fixture. Report verified results and remaining blockers first.
