# Bounded engineering work in Grok Build

Read the complete fixed [workflow](../../vendor/engineering-workflow-core/contracts/workflow.md), [authorization and stops](../../vendor/engineering-workflow-core/contracts/authorization-and-stops.md), and [review and security](../../vendor/engineering-workflow-core/contracts/review-and-security.md) before planning. Read [Grok capability mapping](../../references/grok-capabilities.md) before selecting tools or delegating. These Chinese-authoritative Core bytes define obligations; this skill supplies the Grok mapping and grants no tools or external-write authority.

Establish the current request, repository/branch/HEAD/upstream, complete diff, scope, DoD and single-writer ownership. Preserve unrelated changes. Reuse still-valid evidence and select the smallest coherent implementation. Follow applicable project rules for Issue/branch creation and external actions.

Record task risk from the goal, design, expected behavior and affected data/trust boundaries. Keep unknown risk explicit; reassess when scope, design or impact changes. Follow the effective project policy for check timing, depth and criteria within the mandatory [risk and timing rules](../../vendor/engineering-workflow-core/contracts/review-and-security.md#review-risk-timing). For high-risk work, obtain independent in-depth design review and threat/security analysis early, then code review as implementation becomes available. Start required proportionate scans when a meaningful diff exists; do not wait for a final candidate.

Check the actual loaded public tool schemas and effective model/effort, sandbox and permissions for the selected surface. Keep documented, schema-observed and runtime-verified evidence separate. The offline package/packet commands prove local structure only. Current Grok runtime qualification is incomplete: stop dependent model/tool execution unless the required controlled qualification and authorization already exist. Continue safe independent preparation without lowering DoD.

Use native Grok subagents when they are available, authorized and qualified for the task. Do not substitute Codex dispatch names or build a replacement pool. Assign bounded inputs, source revision, ownership, output and stop conditions. Include relevant risk/check timing, unresolved findings and protected evidence or replacement limits in the brief. A dispatched ID alone is not completion; collect the actual result and verify it. Missing/disabled/unknown delegation means a single writer plus a separately authorized independent reviewer, not author self-approval. Do not create peer sessions or paid API calls merely because a task can be described in a skill.

Implement with fast tests and cheap applicable security checks throughout development. Obtain an independent read-only [change review](../grok-review-change/SKILL.md) for code, documents and bounded security analysis. Use Core's [security applicability rules](../../vendor/engineering-workflow-core/contracts/review-and-security.md#review-security) and [evidence and continuation rules](../../vendor/engineering-workflow-core/contracts/review-and-security.md#review-evidence) for policy, required checks, capability gaps, external evidence and authorized exceptions. Use the Grok mapping's Security method selection section for methods, actual tool/plugin availability, native reviewer/model settings and data boundaries. Complete necessary checks and resolve findings; do not relabel ordinary review as a scan or imply scanner/product equivalence. After changes, bind the new candidate revision/diff and justify affected retests, reviews, necessary rescans and evidence reuse under Core. A plan/persona label is not technical read-only enforcement. If such enforcement is required, demand actual tool/deny evidence.

Synchronize behavior, docs, package and version claims. Apply the shared [plain-writing requirements](../../vendor/engineering-workflow-core/contracts/workflow.md#wf-writing) during Docs Sync and record applicable sampling in the existing document review. For a change request or delivery readiness, read the complete [exact-head contract](../../vendor/engineering-workflow-core/contracts/exact-head-and-evidence.md): verify and independently review the entire base-to-head range for every changed head. Confirm that required evidence is current and sufficient for the final candidate; entering merge review does not itself require another whole-repository deep scan. Separate content readiness, platform enforcement and action authority. External commit/push/PR/merge requires action-specific authority and all applicable gates. Use the delivery entry point explicitly authorized by the current project and request; this skill grants no external-write authority.

At continuation and closeout, apply the [evidence lifecycle](../../vendor/engineering-workflow-core/contracts/workflow.md#wf-evidence-lifecycle). Keep compact cause/fix/revision/scope/outcome and replacement references with required review/merge/acceptance evidence. Verify that a replacement covers the original failure and affected boundaries; unrelated PASS or one intermittent success cannot close it. Protect unresolved, intermittent, security/data-loss, shared and still-referenced evidence. Load indexes and needed sources first; missing sources remain unverified. Context slimming is separate from source deletion. Without a valid retention policy or duration, retain sources and record pending decisions. Actual movement, archiving or cleanup needs policy/protection/reference checks, exact scope, authority and required preview/dry-run; irreversible deletion needs confirmation at action time.

Preserve unresolved questions, checkpoints and uncertain effects. Forward new authorization requests with the full question, original request, session/revision/action/path identity and limits; stop and wait. Never infer consent from timeout, a new session or a fixture. Report verified results and remaining blockers first.
